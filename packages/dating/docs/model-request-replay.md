# Model request evidence and follow-up work

Implemented 20 September 2026. Screening, extraction and synthesis now retain their complete application prompts and strict output schemas **before dispatch**, under `data/workspaces/dating/_requests/inputs/<digest>.json`. Responses retain returned text, parsed output, model/backend identity, usage and reported cost under `outputs/<digest>.json`, linked to the request. Digests identify canonical JSON content; loaders reject changed content. These are durable local evidence, ignored by Git like retrieved source bodies: include them in `data/` backups. Historical calls are not retroactively reconstructed.

A request records family, item, run where supplied, role, system/user messages, schema, prompt digest and selected requested execution settings. Backend/client objects, API keys, environment and authorization headers are not serialized. Requested model, fallbacks and reasoning settings are distinct from the model/backend reported in a result. OpenRouter additionally retains returned response bodies and the initial/repair request bodies when a completion succeeds. Other paths retain application request snapshots, not full provider wire transcripts: unreported routing, fallback steps and effective effort remain unknown. Provider determinism and historical model availability are not promised.

Use `harness.model_requests.load_request(request_ref)` to verify and inspect an input. `request_ref` appears in screening/extraction records, batch records and synthesis proposals; `response_ref` identifies a retained output. A replay experiment should create a new request/result record and disclose changed model/settings, never overwrite the old response or present replay agreement as independent evidence. This module makes no network calls.

## Extraction and batches

Extraction freezes the exact quotable evidence text, coverage inventory, retrieval-quality label and retrieved-text identity. Ingestion verifies quotations against that snapshot and does not reread mutable attachments or reconstruct the old prompt. Prompt/schema digests invalidate outdated resumptions. Provenance stores both request and response references.

Batch submission checks snapshot identity, schema, prompt and execution mode before dispatch. Polling verifies request identity/schema/digest and current-input compatibility. Successfully parsed responses are retained before the current-input comparison, so a later source or prompt change can be audited while its stale result is withheld. Legacy batches without snapshots require resubmission; no snapshot is manufactured from current files. Missing/unexpected items and vanished candidates are reported rather than counted as successfully ingested. The existing current-input guard remains: snapshots enable audit, not automatic publication of stale proposals.

New extraction outputs contain `gaps` and `conflicts`, including when `claims` is empty. Gaps name a kind, description, affected subjects and a bounded next action. Conflicts retain separately located quoted sides and a next action. Ingestion records quotation matches separately from semantic status: even when both sides match, the conflict remains pending semantic review. Missing sides are flagged `unverified_quote`. Input omissions/truncation appear separately as program-observed `input_limits`. CLI extraction totals include these three issue counts. Empty lists do not establish study completeness; no automated recovery scheduler or conflict adjudicator is implied.

The issues survive in immutable extraction history, request-linked output and current candidate extraction metadata. They do not create dates, adopted decisions or supported historical conclusions. File locators are model proposals: whole-input quote matching does not yet verify the exact file attribution, which remains a semantic/provenance review task.

## Synthesis scope

Synthesis groups by source subject ID, retaining catalog IDs as context. Multiple source subjects sharing a catalog ID cannot be silently merged. `max_languoids` must be positive; its historical name now refers to source subjects. Proposals and returned summaries record all submitted and omitted subject IDs. Response validation flags missing/duplicate/unknown subjects, recommendations of another subject's claims and forbidden override suggestions. The reported `reviewed` count includes only structurally valid returned subjects; it does not claim semantic correctness. The model's complete response remains preserved, including invalid suggestions. Nothing is adopted automatically.

## Verification and remaining work

Offline regressions cover input mutation after submission, snapshot tampering and identity substitution, credential omission, stale/legacy batch handling, zero-claim issue retention, shared-catalog subject separation and both input/response omissions. These tests measure workflow behavior, not model accuracy. Full wire-level execution tracing, role-specific comparisons, automatic correction/supplement discovery, section-aware context selection and bounded follow-up scheduling remain in the [harness recommendations](harness-recommendations.md).
